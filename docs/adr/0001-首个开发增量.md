# ADR 0001：开发底座与库存预占验证切片

日期：2026-10-09。状态：已采用，适用于 0.1 开发增量。

## 范围

沿用 Python 技术方案和 PY01–PY09 顺序，先建立可执行工程及真实数据库验证能力。初始 24 表 SQL 已冻结为 Alembic `b0001` 迁移。`b0002` 增加库存需求头/行、永久操作结果，并建立来源外键；控制迁移 `c0001` 建立成员授权及会话读取模型。

本次只交付普通批发需求的库存预占/释放闭环，不构成收货、发货或财务过账。未实现的控制服务、前端、经营资质审核、处方、库存成本和结算流程仍按原计划推进。

## 库存需求模型

`inventory_demand` / `inventory_demand_line` 是库存模块接收上游已审核单据的内部接口记录，不是替代销售订单的完整业务模型，也没有开放 CRUD 接口。未来采购退货、批发销售和零售模块须在自身审核事务中写入/撤销需求；`checks_completed` 默认 false，不能让用户直接勾选作为审核凭据。`eligible_until` 是已完成前置检查的有效边界。

测试自行构造合格来源记录以验证库存算法。经营资质、信用、处方等流程尚未接入，因此库存命令默认关闭，零售和采购退货明确拒绝。序列号商品、受限类别也未开放。后续逐项完成相应规则和集成测试后再启用。

## 事务及锁

同步 `def` 接口在工作线程中完成 Session 的创建、使用与关闭。业务与控制引擎分开，应用启动拒绝 superuser、BYPASSRLS 或能够取得 schema owner 身份的运行账号。业务每个事务都使用 `set_config(..., true)` 设置可信租户，所有 27 张业务表启用并强制 RLS。

预占锁顺序：操作编号互斥 → HTTP 幂等记录 → 主体 / SKU 分配门 / SKU / 商品 / 批次共享锁 → 来源单头 / 行 → 按 UUID 排序的库存余额。锁后重读余额和质量状态，再按效期执行 FEFO；不使用 SKIP LOCKED。候选集合之后新增的收货库存留待下次请求重算。在线候选上限 2000、分配上限 500、单据行上限 50。

释放只减少占用，按来源头 / 行 → 余额 → 预占头顺序锁定。来源状态及付款保护在锁内重查。冻结商品不阻止释放占用。占用到期不自动视为已释放；后续租约工作器负责实际释放，未释放前继续扣减可用量。

本增量不产生库存出入账、成本账或应收应付，没有接入结账期间锁。完整过账命令必须按原技术设计的全局锁序补齐这些前置步骤，不得直接沿用本切片作为发货过账。

## 幂等与事件

HTTP 幂等按租户、操作者、命令、目标和键隔离，先返回同键同内容的已有结果，再检查业务版本。同键异内容冲突。客户端操作号的永久结果与预占同事务保存，换 HTTP 键也不能重复预占。数字字符串和明细顺序在 DTO 边界规范化后计算请求摘要。

变更、审计、Outbox 事件和待投递记录一起提交；失败整体回滚。不存在提交后再写事件的窗口。事件投递工作器尚未实现，READY 记录不代表已投递。仅对数据库明确回滚的死锁/序列化失败做最多 3 次新事务重试；连接丢失返回结果待确认，客户端须保留原操作号和幂等键重试。

## 登录边界

当前业务 API 只有只读会话适配器，校验随机 Cookie 的 SHA-256 摘要、过期/撤销、有效成员、权限版本、上下文代次及写请求 CSRF。核心 API 的控制库账号仅有 SELECT。没有临时登录后门或信任租户请求头的逻辑。

完整 OIDC PKCE、回调 state/nonce、加密 Token 存储、刷新互斥、退出、租户切换、会话签发及撤销管理尚未实现。新增登录服务时必须通过真实 IdP 集成测试。跨控制库与业务库的权限变更与在途事务竞态也仍需按最终授权协议验收。

## 构建与运行

本机 Python 3.14.8 和 uv 0.12.23，依赖在 uv.lock 锁定。部署镜像使用带哈希的依赖导出及固定 Python 镜像 digest，以 UID 10001 运行。开发数据库密码随机生成，业务/控制与迁移/运行账号分离；网络绑定本机。初期迁移禁止破坏性 downgrade；未来恢复演练须以备份恢复验证，不能以这项保护代替恢复能力。

CI 所用动作版本参照 [actions/checkout](https://github.com/actions/checkout) 和 [astral-sh/setup-uv](https://github.com/astral-sh/setup-uv) 官方说明，并固定到提交；本次本地检查不等同于远程 CI 已运行。
