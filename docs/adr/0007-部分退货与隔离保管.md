# ADR 0007：部分退货与验收前隔离保管

日期：2026-10-12。状态：已实现于 0.7。补充 ADR 0006；金额与可重复申请规则以本决策为准。

## 目标与适用范围

普通批次采购与批发销售支持按原过账商品行选择数量、分次退回。新建销售退货必须先登记实物隔离收货，再由独立人员验收。适用于非序列号、非特殊管制品种；冷链专门验收、销毁、换货、跨库位退货和零售 POS 尚未实现。

隔离收货按“尚待本企业验收接收的客户退回实物”管理：记录保管责任与位置，未确认成为自有库存。这一业务假设必须与实际企业的合同和会计政策匹配；产品尚不支持收货时即确认所有权的另一种模式。

## 数量与金额依据

采购、销售正常过账新增 `posting_line.gross_amount / net_amount` 不可变快照，保存当时实际使用的逐行金额。销售分批发货原有累计分摊算法保持不变，快照记录该次发货行的真实结果，不重新计算单价。

新退货使用不可变 `return_line`：关联原过账行，保存本次数量、含税金额、未税金额及按原行分摊的成本。数量与原商品快照的基本单位精度一致，不能使用浮点、指数、小于等于零或超精度值；本次行必须属于原批次。

设原行数量 Q、原行含税 G、未税 N、原出库成本 C，此前已过账退回数量为 x，本次为 q：

- 含税 g = round2(G × (x+q) / Q) − round2(G × x / Q)。
- 设前次累计含税为 gx = round2(G × x / Q)。当 G > 0，未税 n = round2(N × (gx+g) / G) − round2(N × gx / G)；G = 0 时 n = 0。
- 原成本分摊 c = round8(C × (x+q) / Q) − round8(C × x / Q)。
- 全部采用 Decimal、HALF_UP；累计比例运算使用 50 位精度。未税按累计含税分摊，避免单次出现负税额；最后一次退完时，累计金额与成本精确等于原记录。
- 原行对应多批次时，每条实际过账行分别分摊，不把总单金额按所有商品数量平均分配。

销售退货入库恢复 c。采购退货依旧按退回时的批次成本池加权成本出库，最后出清成本池时取全部尾差；原行分摊未税减实际出库成本为采购退货价差，保存在不可变过账结果，尚不生成总账凭证。

## 并发、可退数量及结算

同一原过账允许多张已过账退货，但同一时刻最多一张非 POSTED / CANCELLED 申请。数据库部分唯一索引与经营主体排他锁共同约束。REJECTED 的隔离实物尚未交还，仍占用申请位置。

可退数量 = 原数量 − 所有已过账退货数量。创建申请时从已提交事实计算并冻结本次金额；等待中的申请通过上述单申请规则阻止新的竞争申请。取消或交还后重新申请会重新计算。不能修改申请数量，需取消未收货申请或先交还已收实物，再创建新申请。

往来视图先按原过账聚合所有 POSTED 退货，再与原应收 / 应付关联，避免多次退货导致原往来单据重复出现。未结余额 = 原金额 − 有效核销 − 已退金额；版本随每次过账退货增加。

退货过账要求原单当前未结余额 >= 本次退货含税金额。余额足够时保留已有核销；不足时先撤销相关核销。撤销与退货是两个独立提交的命令，中间状态真实反映已提交事实。退款继续按“该退货单剩余退款上限”与“曾核销原单的原款项剩余金额”双重限制；退款不是银行转账。

## 隔离保管状态机

新销售退货（workflow_version = 2）：

```text
DRAFT ─隔离收货─> RECEIVED ─独立通过─> APPROVED ─过账─> POSTED
  │                 │                      │
  └取消─> CANCELLED └独立拒收─> REJECTED     │
                    │             │        │
                    └─────────────┴─登记交还┴─> CANCELLED
```

采购退货继续 DRAFT → APPROVED → POSTED；DRAFT / APPROVED 可取消，拒绝复核即取消。采购退货不是接收客户实物，不走销售隔离收货。

1. 收货人逐行填写实际数量和批号，必须精确匹配本次申请，填写实际隔离位置，确认全部实物交接。新增不可变 `return_custody`，单据进入 RECEIVED。
2. 隔离保管不写 `stock_balance`、`cost_balance`，不冲减应收，不恢复信用，不可被 FEFO 或销售预占使用。台账是单独的待验保管账；不能与自有库存汇总为可售量。
3. 复核人须不同于制单人和收货人。通过前必须逐行录入准确数量、批号，并确认质量说明；通过后进入 APPROVED。拒收进入 REJECTED，保管记录继续开放。
4. APPROVED 过账再次检查商品资质、批次冻结 / 效期、开放期间、未结余额和原库存效果。库存、成本、应收信用回转以及 `return_custody_close(ACCEPTED)` 在同一事务提交。失败后保管状态保持开放。
5. RECEIVED / REJECTED / APPROVED 可以在全部实物已交还客户后登记交还；追加 `return_custody_close(HANDED_BACK)`，单据取消。无需、也不得通过此操作改变自有库存或资金。已过账不可交还或取消。

当前隔离位置是受长度约束的人工位置说明，不是可调拨的标准库存库位。接收时不支持短收 / 超收或逐行不同处理结论；应按实际一致的申请进行操作。拒收后暂存、交还已覆盖；销毁、转不合格自有库存与部分行验收另行实现。

## 历史兼容与迁移

业务迁移 b0007，仅增量变更；控制库仍 c0007。新增 3 张表全部 FORCE RLS、租户复合外键、只允许追加；业务表总计 55 张。原过账金额快照列可空，不修改或猜测旧行金额。

- 已有退货单保留 workflow_version = 1，其原整批复核 / 过账逻辑可继续使用；已过账视为原批次数量全部消耗，不能再次退。
- 升级后新建退货都采用版本 2。新来源有完整逐行金额则支持部分退货；旧来源没有逐行金额则仅支持整批退货，但新的销售退货申请仍必须隔离收货。
- 不清空原单、原退款或已有审计。原 `return_document` 状态更新权限保持列级限制，金额和来源仍不可编辑。
- 生产升级需暂停业务写入、完成数据库迁移并部署一致版本后再恢复。旧版本程序不能与新版本混跑，尤其旧结算 / 退货逻辑不理解多次退货。

## 接口、权限与恢复

新增 GET `/api/v1/returns/sources/{id}` 返回原行、已退 / 剩余数量和 `partial_supported`。

POST `/api/v1/returns` 新增可选 `lines: [{source_posting_line_id, qty}]`；省略表示申请全部剩余可退数量。创建采用永久操作 UUID + 请求幂等键，防止跨缓存期限重复制单。

新增 POST `/api/v1/returns/{id}/receive`：expected_version、reason、zone_label、confirmed=true、逐行 source_posting_line_id / qty / lot_no。

新增 POST `/api/v1/returns/{id}/hand-back`：expected_version、reason、confirmed=true。GET `/api/v1/returns?entity_id=…&custody_only=true` 提供未结清隔离台账，分页 50 条。

收货与交还复用 returns.write；独立复核 returns.review；过账 returns.post；查询 returns.read。所有写命令复用可信会话、CSRF / Origin / 上下文版本、主体范围、事务、幂等和提交前授权检查。接收 / 交还保留不可变事实及审计；过账仍写库存 Outbox。

已过账重试返回原快照，不重复出入库或结清保管账。收货 / 交还使用现有命令幂等缓存与状态 / 版本限制，缓存期外重复请求会被拒绝；操作者应刷新状态核对结果，不能盲目新增记录。授权撤回探测失败会回滚保管结清与所有库存 / 财务变化。两库授权仍不是跨库原子提交，现有网络故障窗口未消除。

## 验证依据

覆盖真实 PostgreSQL 的多次退货、不同价格原行、数量精度与越界、竞争制单 / 重复过账、保管与可售量隔离、拒收交还、角色职责、租户与主体边界、不可变事实、历史来源 / 老申请、核销保留与退款上限、提交探测回滚。金额单测覆盖零售价、分厘尾差、六位数量与接近金额上限。

真实 Keycloak + 浏览器验证管理员收货、独立质量员验收；分次销售 / 采购退货与退款；拒收交还与只读角色限制。具体运行结果见开发进度和验证记录。
