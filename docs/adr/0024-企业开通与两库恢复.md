# ADR 0024：企业开通与两库恢复

状态：已实现。日期：2026-10-16。

## 问题

新企业需要控制面的身份成员与主体范围，也需要业务面的经营主体和仓库。原演示种子同时附带演示数据，不能作为空白企业开通入口。直接分别写两库并启用成员，遇到中断可能让用户进入没有完整资料的工作空间。

## 决策

1. 新增平台专用开通服务与本机命令，以已映射身份的principal UUID接入现有认证。没有公共HTTP接口、自动注册、密码写入或普通角色提权。
2. 控制迁移c0015增加enterprise_provisioning。稳定request_id、规范化清单摘要和UUIDv5资源编号共同约束重试；清单固定，COMPLETED记录不可更新删除。普通认证/运行角色没有该表权限。
3. 控制库事务先写PENDING，企业及首批成员active=false。业务库以med_runtime和新租户上下文原子写入一个主体、实体仓库、库位及审计，不添加商品或任何库存金额。
4. 业务事务成功后，控制库再次核对待开通资料，在一个事务内启用企业及成员并完成请求。未完成记录保持不可访问；两库提交之间的失败由原清单恢复，不宣称跨库原子事务。
5. 控制连接持有按request_id划分的会话级咨询锁，跨越两段控制事务与业务事务；退出时关闭物理连接，避免将管理角色和锁返回共享连接池。等待上限5秒，失败可重试。
6. 重试只接受原清单和对应业务审计标记；未完成控制成员、主体或仓库快照不一致则保持停用。完成后重试只返回历史开通结果，不重启停用企业，也不覆盖营业后的资料。
7. 初始成员要求恰好一个OWNER和另一位有期初审核权限的成员，确保现有建档、审核与开账能继续。审计标注platform_operator来源、请求编号、理由及指定初始OWNER；该OWNER是业务初始归属，不表示其本人在网站执行了平台命令。

## 边界与后果

平台命令依赖本机开发配置和管理凭据，尚无平台管理网页、开通审批、生产身份开户或套餐计费。本轮为现有身份开通一个新企业工作空间，不扩展企业主体数量维护。不同request_id不会依据信用代码自动去重，平台需核对开通台账。

业务过账仍沿用既有资质、租户隔离、主体权限、职责分离、幂等和版本规则。最小新企业没有期初库存；期初需要经原业务页面独立审核后启用。历史应收应付开账另行规划。

验证包括并发相同请求、三个中断位置恢复、业务审计失败回滚、资料冲突、越权、身份缺失及实际新企业首次期初/采购/批零交易。
