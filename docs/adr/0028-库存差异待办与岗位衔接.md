# ADR 0028：库存差异待办与岗位衔接

状态：接受；日期：2026-10-16。

普通调拨、盘点已经有工作台入口，但在途损失和自有隔离处置仍需查找列表。尤其迟到货物收齐后父调拨移出收货待办，未完成损失申请缺少集中核对入口。

新增四个WorkKind：transfer_loss_review、transfer_loss_post、quality_review、quality_post，分别读取DRAFT、APPROVED状态。沿用单条UNION ALL只读查询、企业RLS、经营主体检查、绑定参数字面搜索、稳定排序及分页，不新增写接口、业务状态或数据库表。

损失项使用原损失ID作为item_id，父调拨ID作为target_id，page=transfers，number为父单号、related_number为损失单号；经已授权原单接口直接加载对应损失详情。判定只依损失申请状态，不限制父调拨状态，因此父单收齐后遗留申请仍可见。取消、拒绝或核销后移出；条件不符导致核销失败时保留，禁止待办查询隐式写入或自动取消。

质量处置项以处置ID作为item_id与target_id，page=quality，区分隔离品放行、隔离品报损显示。DRAFT待审核、APPROVED待过账，已完成/取消不展示；源余额、仓库仅用于关联位置，不把当前可用数量作为隐藏申请的条件。

读取权限继续使用transfers.read和quality.read，写权限与独立审核约束由原服务执行。没有新增角色扩权或按人派单。前端传递初始主体、原单及损失ID；质量页新增企业/权限上下文key，返回普通列表后不携带其它单的损失入口，返回工作台保留原筛选并刷新。

业务库b0026、控制库c0016、75张FORCE RLS表、120条API路径不变；WorkKind实施契约扩充至30类业务环节。升级部署核心API和管理端，无数据库迁移。结果见 [库存岗位验证](../development/库存岗位验证.json)。
