# ADR 0011：同主体调拨、在途库存和分次收货

状态：采用。增量：0.11。日期：2026-10-13。

## 问题与决定

采购、销售、退货和盘点已经共用库存余额、不可变流水与主体批次成本池。本次用同一套数量过账建立跨仓调拨闭环，不为仓库另建成本池。范围是同一租户、同一主体的两个不同实体仓库，普通合格批次，基本单位。

### 单据与事实

业务迁移 `b0012` 新增 `transfer`、`transfer_line`、`transfer_receipt`、`transfer_receipt_line`，全部 FORCE RLS。调拨主单为可变状态投影，其余为不可变事实（运行角色仅 SELECT / INSERT，数据库拒绝 UPDATE / DELETE）。外键携带 tenant，路线仓库外键同时携带 entity，收货行外键同时携带 transfer，避免串租户、串主体和串单引用。

状态：`DRAFT → APPROVED → IN_TRANSIT → PART_RECEIVED → RECEIVED`；可多次停留在 `PART_RECEIVED`。只允许在 `DRAFT / APPROVED` 取消。审核拒绝直接进入 `CANCELLED`。审核人必须不同于制单人，数据库约束与应用同时检查。

申请行固定来源 balance、数量、商品和单位快照。申请及审核不预占，不承诺发出时一定有货。发出时重读并锁定库存和当前商品 / SKU / 闸门 / 批次，再次核验可用量、资质、效期及质量。这是当前有界实现的主动取舍；后续如引入预占，应复用统一 reservation 并明确超时与撤销语义。

### 在途与过账

每主体惰性建立一个 `SYS-TRANSIT` 虚拟仓库，每张发出的调拨建立独立在途库位。相同单据同 SKU / lot 的多来源行可以合并到同一在途余额，但可收数量仍按不可变申请行与已收事实逐行计算。不同调拨拥有不同库位，不能消费彼此在途库存。

发出创建 `source_type=TRANSFER / action=TRANSFER_DISPATCH` 过账，segment 为调拨 ID；每行库存流水 effect 0 扣来源、effect 1 增在途。收货创建 `TRANSFER_RECEIVE` 过账，segment 为独立收货子单 ID；每行先扣在途、再增固定目的库位的合格或隔离库存。库存总量相等，cost_balance 不更新，不伪造零额成本流水，不产生 AR / AP / cash。

`已发数量 = 累计已收数量 + 仍在途数量`。本轮没有损失审批，任何短少都继续留在途，不得自动收齐、强制关闭或直接取消。将来损失核销需独立审批和成本过账，届时扩充守恒式和终态，不能修改原收货事实。

发出和收货都检查当前中国时区业务日的开放期间；不支持客户端任意指定历史业务日。每次过账与单据投影、库存余额、双边流水、审计、Outbox 在一个业务数据库事务中完成。

### 可用性与质量

统一库存 BALANCES 查询增加 `IN_TRANSIT` 不可分配原因，查询可用量和 FEFO 共同使用。采购、批发、零售创建业务限制实体仓库；采购库位选项排除虚拟库，避免每张调拨生成的内部在途库位污染选项上限。

合格收货需再次满足当前商品资质、闸门、效期与批次质量条件。异常实物可登记 `QUARANTINE` 自有隔离库存，成本归属仍在原主体，不能销售。它不同于销售退货接收阶段尚未接收货权的 custody。本轮没有隔离后质量放行 / 销毁入口，也不能用普通调拨把隔离库存改成合格。

### 并发、冻结和幂等

沿用当前主体写锁后锁单据，再锁主数据、批次及库存。每次命令带 expected_version；独立收货操作竞争时，一个成功，其余旧版本失败。余额更新满足 on_hand ≥ reserved + blocked；接收检查数量精度、批号、行剩余量及目的库存 numeric 上限。

创建仓库、创建调拨、分次收货均复用永久操作记录，绑定租户 / 操作者 / 命令种类 / 目标 / 完整请求摘要。同一业务操作更换 HTTP Idempotency-Key 也不会再次执行；冲突内容被拒绝。整单发出同时使用唯一过账业务键和主单 dispatch_posting_id，已发出请求返回原过账结果。接收只通过稳定 client_operation_id 重放，不能凭相同数量猜测重复。

盘点的数据库冻结继续覆盖同主体批次所有余额，因此已有盘点会阻止调拨发出。在新建盘点时增加该成本池在途正数量检查，尚未收齐的批次先完成收货，再允许盘点。不能用盘点将未收到的实物从在途删去。

所有 HTTP 写入接入原 SessionStore.guard，持有控制库授权锁至业务提交并做提交前探测。继承此前同主体写入串行和跨数据库网络故障窗口限制，未宣称生产并发容量或分布式原子授权已解决。

### 接口与升级

新增 9 个核心路径：`GET /transfers/options`、`GET /transfers/candidates`、`GET|POST /transfers`、`GET /transfers/{id}`、`POST /transfers/{id}/review|cancel|dispatch|receive`、`POST /warehouses`，均位于 `/api/v1`。写入 DTO 禁止额外字段，数量仅接收规范十进制字符串；最多 50 行，列表与收货历史分页。

控制迁移 `c0010` 添加 transfers.read/write/review/dispatch/receive 与 warehouses.write，更新成员权限版本并撤销旧会话。新增开关 `MED_TRANSFER_COMMANDS_ENABLED` 默认关闭。生产升级应暂停写入、迁移并部署同版本，再恢复；不能混跑仍将虚拟仓库存当作可用库存的旧服务。

## 验证与后续

真实 PostgreSQL 测试覆盖数量及成本守恒、多来源库位同批次、逐行余量、在途隔离、超收 / 批号 / 精度错误、独立审核、质量变化、期间、盘点互斥、RLS、权限、不可变事实、永久防重、竞争和提交撤权回滚。真实浏览器覆盖新增仓库、双账号审核、发出、先收 8 后隔离收 2、目的库存接入零售和只读权限。

后续主体任务优先处理隔离品质量处置与在途差异审批，再补充主数据修订、多库位 / 包装能力；报表和 AI 后置。
