# ADR 0019：采购到货前变更与重新审核

日期：2026-10-15。状态：0.19 已实现，开发验证版本。

## 业务范围

首笔到货前，允许修改处于 DRAFT / APPROVED 且履约为 OPEN 的采购单。支持更换供应商、同主体实体收货仓库、新增 / 移除 / 更换商品行，以及调整交易包装、数量、含税单价和税率。经营主体、订单 ID、订单号及创建人保持不变。

保存即生效为新待审版本，原批准状态清空；重新审核前不得登记到货或关闭采购余量。它不是“保留旧批准版本继续收货、待新版本批准再生效”的申请副本。取消修改对话框不会保存；保存后不提供一键撤回，可再次修订或取消待审采购单。

只要已有任意到货记录，即使全部待验、全部拒收或尚未入库，也禁止修改采购约定。已收齐、已关闭、已取消同样禁止。本次不处理已到货采购单的数量 / 价格更正、逆向过账、补差、部分行变更和供应商协同确认。已到货单可按原流程关闭未收余量，并新建追加采购。

## 版本、审核与留痕

- purchase_order 增加 revision_no（初始 1）和 revision_editors（本轮参与修改的用户 ID）。每次实际修改增加 revision_no 和既有 version；没有内容变化返回 PURCHASE_UNCHANGED，不制造版本。
- 已审核单首次修改开始新一轮编辑集合；同一待审轮次的后续修改追加人员。原制单人及本轮任一修改人均不能审核通过，批准后清空集合。上一轮修改人可审核由其他人修改的新一轮。
- 更新后的行使用新行 ID，原行 ID 保存在不可修改的审计快照；首笔到货前没有履约引用。客户端修改成功后必须重读详情，不能继续使用旧采购行 ID。
- purchase.revised 保存前后完整采购内容：供应商、仓库、行商品名称 / 编码、基本数量、交易数量、包装快照、单价、税率、总额及原批准人 / 时间；同时记录原因、操作者、版本。
- 新的采购批准 / 取消记录带当时采购内容快照。历史老批准事件原先仅记录原因，不伪造缺失快照；变更前快照会保留其当前批准信息。商品名称为记录事件当时的资料名称。
- GET history 按时间倒序、每页 50 条展示变更及审核事件。复用既有 append-only audit_event，无新业务表。

## API、权限与事务

新增 POST `/api/v1/purchase-orders/{id}/revise`：expected_version、reason、supplier_id、warehouse_id、lines（1–50 行，复用 OrderLine）。不接收 entity_id 或自定义行 ID。复用 purchase.write 和采购写开关、Origin / CSRF / 幂等键 / 企业上下文 / 提交前授权守卫。成功返回 id、version、revision_no、state=DRAFT。

新增 GET `/api/v1/purchase-orders/{id}/history?offset=0`：purchase.read；offset 范围 0–100000；返回 items / has_more。审批仍用原 approve 接口与 purchase.approve，取消仍用原 cancel。核心路径共 100 条，无新增人类角色权限。

先取得原经营主体锁，再重新读取订单，防止等待锁期间另一修改替换了供应商 / 商品行。修改与收货、审核、关闭共用主体 / 订单版本序列；旧版本失败并要求刷新。修改与同键重试不会重复增加版本；任一检查、换算或提交守卫失败，头、行、审计及命令结果整体回滚。

旧供应商或旧商品不再合格不妨碍把它们替换掉；新供应商、商品、包装和仓库必须通过当前资格、范围、冻结与精度校验。主体必须活动。后续审核、收货、验收与入库继续执行原有检查。

## 金额与迁移

建单及修改共用采购行换算 / 计价函数。新版本重新读取所选有效包装并冻结快照；数量和单价按交易单位输入，库存数量精确换算，不能表示则拒绝。退役包装不能被当作新修改版本的有效包装；需明确选择新交易单位，并核对数量与价格。修改没有库存、成本、应付或资金过账。

例如 1 箱 3 个：原 2 箱 × 9 元改成 3 箱 × 12 元，原 6 个 / 18 元快照保留，新版本为 9 个 / 36 元。审核后收到 3 个，按新约定入库含税 12 元。分批金额继续使用既有累计分摊规则，未税额按累计含税金额比例分摊；并非直接用基本数量单独平分未税总额。

迁移 b0020 添加版本字段及已到货采购约定保护，b0021 允许替换未到货待审行：只对 purchase_order_line 增加 med_runtime 的 DELETE 权限，触发器限定为 revision_no > 1 的 DRAFT + OPEN 且未收、未关闭行；已到货 / 已关闭行仍禁止删除。原审计不删除，其他表权限不扩展。已到货表头约定字段及商品行的商品 / 数量 / 包装 / 金额禁止直接改写，累计收货和余量关闭仍可按原流程更新。控制链保持 c0013，69 张 FORCE RLS 表。

需停止业务写入与后台任务，备份并迁移至 b0021 / c0013，再部署一致的 0.19 API、管理端及后台任务。不可混跑不理解修改轮次的旧 API。旧采购单初始为第 1 版，不重算历史金额。

## 验证与边界

专项覆盖 26 项 PostgreSQL 测试：修改后重新审核并入库、多修改人职责分离、轮次、待审取消、已到货各状态拦截、包装金额、供应商 / 仓库 / 商品替换、无变化与无效内容、撤权回滚、同键 / 多人 / 收货竞争、历史分页、数据库保护及 HTTP 权限 / 开关。

真实 OIDC + Edge 用例验证包装单位不丢失、修改前后对照、质量人员审核、按新单收货入库、只读查阅及越权拒绝。最终结果见开发进度和验证记录。既有两库授权最终提交故障窗口、生产容量验证和本机虚拟验收数据边界保持不变。
