# ADR 0006：原过账批次整批退货与退款登记

状态：0.6 开发增量已实现，2026-10-11。承接 0.5 采购、销售及核销事实。本轮范围为普通批次商品按一次入库过账或发货子单整批退回；任意部分数量、换货、特殊品种和召回另行扩展。

## 范围与取舍

一次退货对应一个原过账批次，包含该批次所有行、数量、批号及完整应收 / 应付金额。一张采购订单分次验收入库，可以分别退各次入库；销售分次发货可以分别退各张子单。当前不能从同一过账批次只选部分商品或数量。

原出入库单、数量流水、成本流水和原应收应付保留。退货单追加反向库存效果及财务冲减，原销售履约数量不回退，订单不自动重新打开；需要补货时另建新单。选择整批边界可以直接采用原整笔含税、未税和税额，避免在缺少原逐行金额快照的历史数据上猜测部分退货金额。

退回实物在复核和过账前应单独隔离保管。申请本身不增加库存，不具备完整电子隔离收货台账；本轮只接纳独立复核通过的普通商品，销售退回品过账时再次检查商品资质、批次效期及冻结状态。拒绝复核取消申请，不自动执行实物处置或退回客户。

## 状态、身份与数据

流程为 DRAFT → APPROVED → POSTED；待审核或已审核可以取消，拒绝复核进入 CANCELLED。申请人不能审核自己创建的退货，也不能完成其过账；审核人员逐行输入实物数量、批号并记录质量结论。原来源每次只允许一张非取消的退货单。

| 对象 | 用途 |
| --- | --- |
| return_document | 原来源、往来、金额、申请原因不可由运行角色修改；保存独立审核、状态、过账关联和版本 |
| cash_refund | 关联原收付款及已过账退货，保存实际退款方向、原账户、金额、日期、凭据；原始字段不可改 |
| cash_refund_void | 更正错误退款登记的不可变凭据，一笔退款最多作废一次 |
| cash_document.refunded_amount | 有效退款累计投影，与已核销金额之和不得超过原款项金额 |
| settlement_item.returned_amount | 已过账整批退货冲减；视图继续以执行者身份应用源表 RLS |

业务迁移 b0006 新增 3 张 FORCE RLS 表，合计 52 张；控制迁移 c0007 增加退货权限并撤销旧权限会话。迁移保留全部既有数据，旧应收应付的已退货额为零。

OWNER / ADMIN 可申请、复核、过账，但仍受人员分离限制；OPERATOR 可申请和取消；QUALITY 可复核及过账；FINANCE / VIEWER 可读取。退款登记及作废需要 finance.reverse，退货界面也可通过原核销接口撤销相关核销。

## 库存与成本事务

命令获取主体行排他锁，校验开放期间、状态、权限与版本，并协调商品、批次、库存和成本池行锁。

销售退货将全部原出库数量恢复到原库位，将每条原出库成本精确加回原主体批次池；原数量 / 成本流水分别通过 reversal_of / origin_cost_entry_id 关联。采购退货检查原库位可用量和当前成本池数量，按当前批次加权成本移出库存；末次耗尽池数量时结转全部残余成本。原采购未税金额与实际移出成本的差额保存在不可变过账结果，作为后续会计凭证的价差依据。

退货过账、库存投影、成本投影、不可变流水、应收应付冲减、客户信用、审计和 Outbox 在同一业务事务提交。销售退货冲减客户应收，未发订单敞口不变。任一校验失败全部回滚。采购退货不改变客户信用。

## 已核销原单与退款

```text
有效未结余额 = 原始应收 / 应付 − 有效核销 − 已过账退货金额
原款项可用余额 = 实际收付款金额 − 有效核销金额 − 有效退款金额
```

整批退货必须先撤销原单全部有效核销。系统列出原款项号及核销金额，财务人员逐笔填写理由撤销。撤销会恢复应收及信用占用；退货过账再冲减完整原金额。这两个步骤独立提交，未完成退货前债务和信用仍按实际状态展示，不静默改写历史分配。

销售退款为向客户付款，采购退款为收到供应商款项。两者均只登记现实中已发生的资金流动。可选原款项须曾核销过本次退货对应原单，且仍有可用余额；主体、往来、资金账户必须匹配，方向相反。退款金额同时受原款项余额和退货剩余金额约束，支持分次、多个原款项。未付款退货无需退款；页面显示的“尚未登记退款金额”不是自动生成的退款应付款。

退款不生成可再次核销的普通收付款记录，避免同笔资金重复使用。普通收付款和退款之间检查相同账户、方向和凭据编号防重。退款实际日期不能晚于北京时间当天，对应期间必须开放。

作废退款登记仅用于错误登记更正：追加作废事实、恢复原款项可用余额和退货退款余量，不撤销退货、不改变应收，也不撤回银行转账。原款项存在有效核销或退款时不能作废。没有银行直连或自动资金转移。

## 幂等、隔离与接口

退货申请、退款登记、退款作废复用永久客户端操作号及请求指纹；退货过账按原单唯一性和不可变过账结果保持永久防重。退款与核销共用主体锁，现金版本在退款和作废时递增。视图版本在退货过账时递增，旧核销请求会失效。

新增接口：

- GET /api/v1/returns/sources：按主体及采购 / 销售来源分页。
- GET / POST /api/v1/returns：列表 / 申请。
- GET /api/v1/returns/{id}：原批次明细、复核和有效核销。
- POST /api/v1/returns/{id}/review、/cancel、/post：复核、取消、过账。
- GET /api/v1/returns/{id}/refund-options、/refunds：原款项选项、退款记录与余量。
- POST /api/v1/return-refunds：实际退款登记。
- POST /api/v1/return-refunds/{id}/void：更正错误退款登记。

运行核心 OpenAPI 共 47 条路径。新写入开关 MED_RETURNS_COMMANDS_ENABLED 默认关闭，由本机 dev.py 开启。列表、关联核销、退款及款项选项每页 50 条；一次原过账最多 500 明细。页面按企业上下文卸载重建，异步响应过期后不更新页面。退货页面按需加载。

两库授权共享锁与提交前探测继续沿用，存在网络故障窗口，不能宣称跨库原子提交。主体串行化和结算视图尚无生产容量测量。

## 验证与后续

16 项新增 PostgreSQL 测试覆盖双向退货与退款、原成本恢复、当前成本及价差、已核销拦截、原款项关联、分次退款、退款及核销余额共用、并发申请 / 过账 / 退款去重、错误登记作废、权限和不可变事实、不同租户 / 主体、实物核验、冻结重检、未来退款日期、版本冲突及提交前授权失败回滚。

浏览器验收使用真实 Keycloak 和独立管理员 / 质量员会话：采购 10 件、销售 3 件、收款核销 60 元、退回 3 件并分次退款 20 / 40 元，再将采购 10 件退回并收回供应商 130 元。另验证只读用户无法发起退货。

下一步：部分退货及逐行金额快照、电子隔离收货与质量处置、跨库位退货、换货、退款独立审批与附件、财务对账、零售 POS、盘点和调拨。采购退货价差尚未生成总账凭证，退货过账后的纠错 / 红字再冲回尚未开放。
