# ADR 0015：仓库与多库位维护

状态：已实现，0.15，2026-10-14。

## 目的与范围

采购收货和调拨已经按 location_id 入账，但原入口只能随新仓库建立首库位。补齐独立的实体仓库检索、库位新增及名称更正，让业务能直接使用现有仓库的新库位。入口为“资料 → 仓库与库位”；调拨页保留新建仓库的便捷入口。

本轮不改变仓库身份：仓库编码、经营主体、类型及库位编码、所属仓库在 API 中不可修改。没有停用、删除、跨主体迁移、库位合并或同仓移库。库位名称是业务显示信息，不表示温区、许可或质量状态；库存质量仍由余额状态和既有验收流程控制。

## 数据与服务

- b0016 为 med.location 增加可空 name varchar(200)，非空时须去除首尾空格且有内容。历史、种子及系统在途库位没有名称时，读取返回编码作为名称，不伪造历史维护记录。新实体仓首库位名称默认等于编码；新增库位显式提供名称。
- 仓库、库位继续使用现有 tenant_id 复合主外键及 FORCE RLS，不新增业务表。仓库编码在主体内唯一，库位编码在仓库内唯一，现有区分大小写规则保持不变。
- WarehouseService 负责维护，原 TransferService.create_warehouse 作为委托兼容入口。新建仓库沿用原 warehouses.create 操作名、请求结构和永久业务操作号，旧请求重试保持原结果。
- 仓库列表、库位列表、仓库维护记录分别每页 50 条。库位和历史使用独立 offset；仓库/库位可按编码或名称检索。读取不返回系统在途仓。
- 库存可用量响应增加 location_id / location_code / location_name；采购和调拨库位选项带名称。名称为当前值，历史单据仍保留原 ID、原过账事实；关联当前名称的列表会显示更正后的名称。

## 写入一致性

新增实体仓与首库位原子提交。向已有仓库添加库位，必须带仓库 expected_version；名称更正使用被更正仓库或库位的 expected_version，拒绝无变化请求。新增库位或库位改名也增加父仓库版本及更新时间。

写锁顺序为主体 → 仓库 → 库位。主体锁沿用进销存命令串行化策略。名称更正不生成库存 / 成本过账，不改变 on_hand、reserved、blocked、成本池或业务单据状态；正在执行的采购、调拨仍按原 ID 校验。系统在途仓和其库位不允许人工维护。

新增操作使用 client_operation_id 的永久防重记录，HTTP 幂等缓存过期或使用新 HTTP 键后仍返回原结果。同一操作号换内容、调用人或目标均拒绝。名称更正复用 HTTP 幂等与版本检查：同键返回原结果，缓存过期后旧版本请求不会再次修改。

每次成功维护在同一事务追加 warehouse 资源审计，包含操作人、请求、原因及改名前后名称；新增库位包含库位 ID、编码、名称。现有不可变审计规则继续生效。失败或提交前撤权，资料、版本、审计及幂等记录一并回滚。

## 接口与权限

| 接口 | 用途 | 权限 |
| --- | --- | --- |
| GET /api/v1/warehouses?entity_id=&search=&offset= | 主体实体仓检索 | inventory.read |
| POST /api/v1/warehouses | 新仓与首库位，保留旧请求 DTO | warehouses.write |
| GET /api/v1/warehouses/{id}?search=&offset=&history_offset= | 仓库、库位及维护历史 | inventory.read |
| POST /api/v1/warehouses/{id}/rename | 修改仓库显示名称 | warehouses.write |
| POST /api/v1/warehouses/{id}/locations | 新增库位 | warehouses.write |
| POST /api/v1/warehouses/{id}/locations/{location_id}/rename | 修改本仓库位显示名称 | warehouses.write |

读取和写入均检查租户及主体范围，写入在读取幂等缓存前检查资源权限，库位改名同时核实父子归属。OWNER / ADMIN 可维护，其他有 inventory.read 的角色可读。复用既有权限，无控制库迁移或会话强制撤销。

仓库维护统一使用新增 MED_WAREHOUSE_COMMANDS_ENABLED，默认 false，本机 dev.py 启用。旧新建仓库接口从调拨开关移到该开关；部署时须明确配置，调拨开关本身不再允许仓库维护。Origin、CSRF、上下文代数和提交授权栅栏沿用现有实现。

## 验证与边界

真实 PostgreSQL 测试覆盖：新库位采购入库、在途改名后调拨收货、数量成本与原库存 ID 保持、并发版本冲突、永久防重、只读角色 / 租户 / 主体隔离、父子归属、停用主体、系统仓保护、审计不可变、分页以及四类维护命令撤权回滚。HTTP 验证独立开关、参数和角色拒绝。浏览器通过真实 OIDC 维护及入库，并在库存查询显示库位。

管理端列表已分页；采购/调拨等既有选项仍有容量上限（采购选项各 200、调拨仓库 200 / 库位 500，单商品库存查询最多 200 条）。超过上限明确报错，不截断后静默选择；规模化选项分页属于后续工作。本轮没有生产负载容量结论。

升级先迁移 b0016，再启动一致版本服务并配置开关；不需要重过账或搬迁库存。当前响应扩展与内置契约同步，严格响应校验的外部客户端须更新 AvailabilityItem。原规划 OpenAPI 保留，已实现路径另行导出。
