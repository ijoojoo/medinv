# ADR 0026：提交异常恢复与原单继续

状态：接受；日期：2026-10-16；版本：0.24追加。

## 问题

原管理端useCommand仅在组件内存保存请求幂等编号。服务器已提交而响应丢失时，刷新页面、卸载组件会丢失原编号，重新建单可能形成另一笔业务。已有数据库事务、命令幂等及原单待办需要一个跨页面刷新的前端恢复入口。

并发验证还发现新销售岗位取消发货时会进入默认要求inventory.release的内部释放方法，从而无法完成本来具有sales.write权限的原单取消。

## 决策

1. 新增commandRecovery模块，在请求发送前把路径、序列化请求、幂等编号、账号、企业、时间写入sessionStorage；保存失败则不发请求。作用域为principal_id + tenant_id，不绑定会话代数，使重新登录仍可找回。每个作用域仅一笔未确认命令。
2. 公共useCommand复用该模块，仍保留组件卸载和上下文变更后的回调隔离。页面加载仅读取恢复记录，不自动发送；人工点击“继续原提交”或原表单提交完全相同的内容时，才使用同一请求和编号。内容不同的命令在恢复前拦截。
3. 单次等待20秒。首轮明确业务4xx拒绝允许修正；网络错误、5xx、不完整响应、未知网关错误或408保留记录。恢复请求后续出现4xx仍保留记录，避免把权限变化或版本冲突误判为首次操作未保存。成功确认后清除记录并刷新工作台。
4. 自动重放范围限制在创建后24小时内，短于现有服务端幂等记录的7天期限字段。超时、损坏记录通过人工核对入口处理，需勾选声明；清除本地记录不产生业务命令或撤销交易。浏览器时钟异常也阻止自动重放。
5. 记录只接受同源/api/v1/路径、对象JSON及最多1MiB字符的请求内容；不保存认证信息。账号和企业切换清除显示，保留原作用域记录；继续提交始终使用当前会话。这个本地隔离不是服务端授权边界，服务端权限与RLS继续执行。
6. 销售取消内部调用释放方法时显式传入sales.write，保持销售单与发货单锁定、主体验证、状态和数量检查；不扩大SALES角色权限，也不改变通用库存释放接口。零售原有权限路径保持不变。

## 代价与范围

sessionStorage不会保证关闭标签页或换设备后恢复，也不是多标签页协调机制。选择它是为了先补齐同标签页刷新与重新登录的主线中断场景，避免在当前阶段引入服务端草稿、全局命令任务或离线同步架构。浏览器记录损坏时采用停止写入、人工核对的处理方式。

恢复成功后统一回工作台，由原单列表或待办继续，不在恢复模块复制各业务表单状态。前端不能保证实物或实际现金操作幂等，这仍由原单核对与岗位人员确认。

本轮没有新增迁移、权限码、依赖或API。数据库仍为b0026/c0015，75张业务FORCE RLS表、120条API路径及26类业务待办。

## 验证

真实提交后丢失响应及不完整成功响应、换企业/账号后原记录恢复、后续权限拒绝不丢原记录、存储不可用不发送、过期/损坏记录需勾选人工核对；批零同时竞争、缺货取消后同请求恢复、同一过账重复提交不重复扣库存、销售取消权限及通用释放越权拦截。执行结果及相关页面回归范围见 [验证记录](../development/提交异常恢复验证.json)。
