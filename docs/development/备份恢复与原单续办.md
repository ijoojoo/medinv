# 本机备份恢复与原单续办

本轮交付本机试用环境的加密备份、独立恢复及未完成原单续办演练。工具固定为“复制到新环境”，不提供覆盖原库、自动升级或将演练数据合并回原环境的命令。验收完成后原环境已恢复运行，恢复副本停止并保留数据卷。

## 实际验收结果

原企业“恢复验收企业-31763659”通过真实业务接口建立10件合格库存，再准备采购5件已验收待入库、批发4件已拣货待复核、零售2件实收40元待交付。备份时原库存10件、预占6件、成本115.04元、采购应付130元。

将业务库、控制库和身份库恢复到全新数据库集群，三个库共186张表的记录数与备份一致，业务版本b0026、控制版本c0016及75张FORCE RLS表一致。数据库角色、对象所有权和授权随原备份恢复，没有使用跳过所有权或跳过授权的恢复方式。

恢复副本验证了原浏览器会话及加密刷新令牌仍可使用，七个岗位原账号可登录、权限集合一致，未加入企业的只读账号不能切入。通过页面原单入口继续采购入库、批发复核出库、零售交付，再由财务办理实际款项登记及核销。原40元零售收款请求和采购入库请求分别重复确认，均只记账一次。

恢复副本最终9件、预占0、成本103.536元，4条库存流水与4条成本流水一致；采购应付195元、批发应收80元均核销为0，零售只保留一笔40元收款。款项为虚拟验收记录，不涉及支付机构转账。另以正常运行账号、租户RLS和只读事务核对数据库结果。

切回原环境后，再次真实登录七岗并核对三张原单、库存及资金记录。原环境仍为备份时的未完成状态：10件、预占6件、成本115.04元、一笔40元收款、采购应付130元；副本的过账和核销没有写回原库。

## 操作前提

- 已按[试用部署操作指引](试用部署操作指引.md)运行六个容器服务；备份前原环境须全部运行。
- 使用项目后端虚拟环境中的Python，依赖已经锁定的cryptography、SQLAlchemy和psycopg，无新增依赖。仅统一启停工具可使用纯标准库Python，恢复工具需要后端依赖。
- 保留当前运行的六个镜像。备份记录实际镜像ID，恢复前逐个核对本机存在相同镜像，不自动替换为同名新镜像。备份不包含镜像。
- 预留新数据库卷的磁盘空间，以及55433、8081两个演练端口；恢复应用临时使用原5173地址，保持原身份issuer、回调和会话校验。
- 在维护时间执行，停止其他开发服务、平台开通、手工SQL等写入工具；演练入口开放期间不要办理真实业务。超级用户仍可以绕过普通连接限制，因此不能把维护工具当作对其他数据库管理员的写入隔离。

## 备份

在项目根目录执行：

```text
backend/.venv/Scripts/python.exe scripts/recovery.py backup
```

工具先核对交付指纹，记录原数据库连接限制和运行服务，再停止页面、业务、认证、后台回收及Keycloak。将三个库的普通连接上限临时设为0，拒绝新的普通运行账号连接，并检查没有残留客户端；随后分别导出数据库和全局角色、记录逐表数量、运行配置和身份主题。无论导出成功与否，正常错误路径都恢复原连接限制及服务。

单库SQL导出不自动提供跨库同一快照，因此本工具使用维护窗口暂停全部写入后顺序导出三库；相关行为依据[PostgreSQL 18 SQL Dump](https://www.postgresql.org/docs/18/backup-dump.html)和[角色备份说明](https://www.postgresql.org/docs/18/app-pg-dumpall.html)。备份仍要求期间不进行其他超级用户写入。

成功后输出备份编号、文件路径、SHA-256及大小，不输出密钥内容：

| 文件 | 位置 | 用途 |
| --- | --- | --- |
| 加密备份 | `.cache/backups/备份编号.medbackup` | 三个数据库、数据库角色、原配置和身份主题 |
| 独立恢复密钥 | `.cache/recovery-keys/备份编号.key` | 对应备份的认证解密 |
| 维护记录 | `.cache/recovery/source-maintenance.json` | 中断后恢复原连接限制及服务，正常结束删除 |

采用Fernet认证加密，文件损坏或密钥不匹配时先拒绝解密，不创建恢复数据库。密钥与备份应分别保管并另存到独立介质；本机自动生成的两个目录都位于同一工作区，尚不构成异地容灾。备份包含全部租户数据、角色凭据和会话资料，不可作为公开试用包分发。工具的文件模式设置不等于Windows ACL或密钥托管设施。

## 恢复到新环境

将下列`BACKUP_ID`替换为成功备份返回的编号：

```text
backend/.venv/Scripts/python.exe scripts/recovery.py restore --backup .cache/backups/BACKUP_ID.medbackup --key .cache/recovery-keys/BACKUP_ID.key
```

工具验证加密认证、每个条目指纹、兼容版本及镜像，然后生成新的`medinv-restore-十二位编号`项目。只允许使用新目录和新数据卷；恢复失败保留停止的现场，重新恢复会生成另一项目，不清空重用旧卷。

新PostgreSQL不运行原演示初始化脚本；先恢复角色，再创建并恢复三个数据库，保留所有权和ACL。恢复后还原原连接限制，核对逐表数量、版本和RLS。成功输出目标项目名。此阶段只有副本数据库运行，原应用继续提供服务。

## 切入演练与结束

将`TARGET`替换为上述成功恢复返回的项目名：

```text
backend/.venv/Scripts/python.exe scripts/recovery.py start --target TARGET
backend/.venv/Scripts/python.exe scripts/recovery.py assert-target --target TARGET
```

工具再次暂停并限制原环境写入，然后在独立网络和独立数据库上启动恢复应用。恢复Keycloak从身份库读取原账号，不重新导入realm或重建管理员。原源数据库与副本使用不同的集群标识、数据卷和宿主数据库端口，应用入口仍为5173；`assert-target`检查该入口确实属于指定副本，且原写入服务已停止。

用原账号登录，按正常待办继续原单，确认库存、成本、往来和款项后结束：

```text
backend/.venv/Scripts/python.exe scripts/recovery.py stop --target TARGET
backend/.venv/Scripts/python.exe scripts/trial.py status
```

停止副本所有服务，保留独立卷，并按维护记录恢复原服务。副本禁用自动重启，避免机器重启时争用原入口。切回后重新登录原环境。不要将副本当作正式环境继续营业，也不要尝试直接合并两边已发生的过账。

## 中断处理

普通导出失败、残留外部连接等会自动恢复原服务；开始演练失败会停止副本再恢复原环境。终端被强制结束、Docker中断等情况可能留下维护记录：先核对Docker及原PostgreSQL仍是原容器，若副本入口还在运行，先执行对应`stop --target TARGET`，再执行：

```text
backend/.venv/Scripts/python.exe scripts/recovery.py resume-source
backend/.venv/Scripts/python.exe scripts/trial.py status
```

存在运行中的副本入口时，工具拒绝直接抢回地址；原数据库容器标识改变时，也拒绝把旧维护记录应用到其他容器。此类情况需核对现场，不要删除维护记录或重新初始化原数据库。

## 验证与适用范围

工具专项25项通过，包含新增14项恢复边界和原11项部署测试；新增场景分别以prepare、resume、source三个阶段运行且全部通过。默认全站测试会跳过这个维护场景，只有显式设置`MED_RECOVERY_PHASE`才运行。浏览器续办前必须指定并核对`MED_RECOVERY_TARGET`，原会话文件仅保存在忽略目录`.cache/recovery-scenario/`。未在本轮重跑完整后端或全站浏览器。

独立账本核对使用`scripts/verify_recovery.py`；传入`--target TARGET`核对副本的已完成结果，不传则核对原环境的未完成基线。这是本次验收专用检查，不是通用业务报表。详细证据见[备份恢复验证](备份恢复验证.json)。

当前仅完成同一主机、同一应用和数据库版本的维护窗口恢复演练。工具将备份条目在内存中打包、加解密，条目合计上限256MiB；不适用于大规模在线备份。未覆盖异机灾难恢复、时间点恢复、自动定时/异地备份、生产密钥管理、过期会话恢复或长期停机后的所有单据状态。备份不暂停业务时间、资质有效期或预占期限；本次在有效窗口内续办，过期单仍按现有规则处理。
