# 提交异常恢复操作指引

适用版本：0.24追加交付，2026-10-16。优先解决采购、销售、库存和收付款办理过程中“是否已经保存”的不确定性。

## 出现“上次提交的结果待确认”时

1. 保留当前浏览器标签页，停止重复制单、收付款或实物交付。页面会保留原操作内容；刷新、切换菜单后仍可显示待确认入口。
2. 点击“继续原提交”。系统使用原内容和原提交编号重新办理：后台已经成功的请求返回原结果；尚未成功的请求按当前业务规则执行。此按钮包含继续提交的动作，不是单纯查询。
3. 确认成功后进入企业工作台，从业务列表或待办继续原单。采购制单会显示返回的原单号；已收款零售应从“零售待出库”进入原单核对批号、数量并完成交付，无需再登记收款。

待确认期间，该标签页中同一账号、同一企业的新业务提交会被拦截，查询仍可使用。切换企业或账号不会将原提交送到新企业；回到原账号、原企业后再确认。恢复过程使用当前登录会话，原有岗位、主体、资质、版本及库存检查继续生效。

## 无法继续确认时

初次提交明确返回数量、批号、版本等业务校验错误时，可修正内容再提交。网络中断、等待超时、服务错误、返回内容不完整时保留待确认记录。已经发生响应丢失后，即使再次提交被权限或版本检查拒绝，也不能据此认定第一次没有保存；仍需核对原业务。

提交超过24小时，或浏览器记录损坏时，不再自动重放原内容。到原业务列表核对单据、实际库存和现金凭据；必要时请有权限的同事核对。确认完成后点击“已人工核对，结束确认”，勾选核对声明，结束本次确认。此操作只清除当前标签页的恢复记录，不撤销单据、不释放库存，也不退回款项。更正业务仍须在原流程中办理取消、退货或退款。

如果提示“本页无法保存提交恢复记录，本次未发送”，本次操作尚未发往后台。恢复浏览器存储能力后再试；不要通过关闭保护重新制单。

## 缺货和批零同时销售

批发与零售共用库存预占。库存10件时，两位销售人员分别申请7件，只能一方成功，另一方收到缺货提示；失败的一方不会留下半笔收款或额外库存扣减。

未实际交付的占用，可由有权限的人员从原发货单或未付款零售单取消，释放库存。另一方核对可售数量后继续原业务。销售员现在可以取消原未过账发货单并释放它的预占，无需赋予通用库存释放权限；已经出库的单据仍走退货流程。

## 当前边界

- 恢复记录属于当前浏览器标签页，按账号和企业区分。支持该标签页刷新、菜单切换和重新登录，不保证关闭标签页、清除浏览器数据或换设备后仍可恢复。遇到这些情况，应从后台业务列表核对原单。
- 仅保存业务路径、原请求内容、提交编号和时间，不保存登录口令或会话令牌。成功后清除；异常记录在核对前保留。
- 同一标签页一次只处理该账号、该企业的一笔待确认业务。不同标签页、不同设备之间不提供待确认全局锁；多人共享同一账号不属于推荐工作方式。
- 系统登记实际现金凭据，不实际执行银行扣款、退款或自动实物交付。恢复按钮不能代替收银员对现金和交付事实的核对。

## 开发验收入口

管理端目录执行 `pnpm run test:recovery`。场景使用真实登录与业务数据库，在后台实际提交后截断或损坏响应；覆盖采购去重、收款去重、页面刷新、企业及账号隔离、后续权限拒绝、存储不可用、记录损坏和过期人工确认。

后端新增 `tests/integration/test_channel_recovery.py`，验证批零并发、两种缺货释放方向、原请求重试、数量成本守恒和销售取消权限。范围及实际执行结果见 [提交异常恢复验证](提交异常恢复验证.json)。
