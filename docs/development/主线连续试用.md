# 同批商品的进销存连续试用

日期：2026-10-16。业务版本0.24，业务库b0026、控制库c0014。

本次在演示批发企业中，用同一经营主体、同一普通器械SKU和同一批号，连续完成采购、批发、零售、三类退货、分次调拨、盘点、再次销售与收付款核销。各业务共用真实数据库和原业务接口；制单员与质量审核员使用各自登录会话，退货、调拨、盘点从工作台进入原单办理。

结果：两个实体仓库最终剩2件和1件，在途为0，可售合计3件；共享成本池数量3件、金额34.512元。客户应收、供应商应付均核销为0。与本次单据关联的业务待办全部结清，没有发现主线阻断问题。

## 验收人员和数据

- 制单 / 仓储 / 收银 / 结算：演示企业管理员demo.owner。
- 独立审核 / 复核 / 过账：演示质量审核员demo.quality，按现有角色权限办理。
- 每次运行建立两个专用实体仓库、一个测试SKU、一个供应商兼客户、一个测试现金账户；编码带本次运行标识，避免混用既有业务。
- 采购10件，含税单价13元，税率13%，采购应付130元、入库成本115.04元。批发、零售含税单价均为20元。
- A仓用于采购与初次销售，B仓用于调入、盘点及再次零售；同主体同批次共用成本池。

## 跨业务衔接检查

1. 调拨首次收货后，同批仍有1件在途。目的仓申请盘点被COUNT_IN_TRANSIT拒绝，不能在成本池仍有在途时冻结盘点。
2. 调拨收齐后在B仓建立盘点。虽然只调整B仓选中的库位，同主体同批号在A仓也被冻结；两个仓库的零售建单均被COUNT_FROZEN拒绝。
3. 盘亏过账后两个仓库均恢复可售，B仓继续完成零售，证明冻结不会残留阻断后续业务。
4. 两次零售交付均重复提交原过账请求，返回原过账结果，未重复出库、重复扣成本或重复收款。
5. 已完成的采购、批发、零售、退货、调拨、盘点及结算凭据在本次待办查询中没有未结事项。

## 重复运行

先按README启动开发数据库、身份服务、认证服务、核心API及管理端，并准备演示账号。运行过程中暂停独立预占回收进程，避免与涉及时间控制的其他测试互相影响；完成后恢复。进入apps/admin-web执行：

```text
pnpm run test:mainline
```

这条命令同时运行真实登录业务流程及只读余额核对。仅在本机开发演示环境运行，会通过正常业务命令新增虚拟验收单据和审核记录，不删除历史单据。盘点发生中途失败时，清理逻辑会取消本次未结束盘点以释放冻结。

如需针对最近一次已完成场景重新核对余额，在项目根目录使用backend虚拟环境Python运行scripts/verify_mainline_trial.py。该命令仅核对固定的验收预期，不是任意企业的通用对账工具。

自动结果保存于：

- artifacts/mainline-trial-reconciliation.json：本次商品批号、原单ID / 单号、12个核对节点和库存流水。
- artifacts/mainline-trial-db.json：只读数据库余额核对结果及各单据最终状态。
- artifacts/mainline-trial-ledger.png：实际库存台账页面截图。
- docs/development/主线连续试用验证.json：本次运行范围、测试结果和证据摘要。

记录中的documents仅保存原单引用，避免把创建时的草稿状态当作最终状态；最终状态见只读核对记录。
