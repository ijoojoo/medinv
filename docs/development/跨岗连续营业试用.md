## 连续营业路线及核对数

使用同一主体、同一普通器械、同一批次；初始库存为0。采购10件，每件含税13元，税率13%；批发与零售每件含税20元。成本保持原批次精度，不逐条舍入为两位小数。

采购、批发退货发生在对应往来款结算前，直接冲减原往来义务；已核销后再退货、撤销原核销及实际退款另由[退货岗位交接](退货岗位交接.md)覆盖。

盘点冻结期间，总仓和门店仓对同批次的零售建单均被拒绝。质管审核、过账后恢复营业，门店实际完成下一笔零售。退货、盘点和财务办理后，全企业待办为0，所有预占与冻结数量为0。

## 两次提交恢复

自动验收分别在“合格入库”和“登记现金收款”时，让后台真实保存成功，再截断返回页面的响应。先查询后台，确认库存或收款已经存在；然后刷新同一标签页，检查没有自动重发，点击“继续原提交”。恢复时请求内容及幂等编号与原请求一致，后台返回原结果。

入库恢复前后均只有一份10件库存和130元应付；收款恢复前后均只有一笔40元实收，交付前仍为6件库存。随后从原零售待办完成出库，并继续办理原单退货及退款。

这里覆盖页面刷新后的恢复和原单跨岗继续。关闭标签页、清除浏览器数据、换设备或服务重启后的恢复不在本次新增场景范围；既有恢复限制见[提交异常恢复操作指引](提交异常恢复操作指引.md)。此次没有修改业务权限、提交恢复规则、数据库结构或业务接口。

## 多企业待办查询阻断修复

相关页面回归时，旧演示企业的待办首次加载超过5秒，数据库日志确认该查询触发原有语句超时。新企业的连续营业已通过。进一步以普通业务账号、租户隔离及只读事务复现：同一连接先为小企业建立通用缓存执行计划，再查询大企业时超过30秒仍未完成；直接针对大企业重新规划则能迅速完成。初步排查的JIT开关不是该现象的原因。

业务待办现在仅在自身只读事务内设置 `plan_cache_mode=force_custom_plan`，使已准备语句也按当前主体、搜索和当前租户统计估算重新规划。数据库仍执行同一条联合查询，维持统一快照、排序和分页；结束事务后自动恢复连接原设置，不影响下一企业或其他业务命令，也未提高5秒业务超时。

本机同条件对照中，先准备小企业计划、再查询旧企业，修复后的两次查询含规划及客户端调用约56.7毫秒和55.7毫秒。该结果是本机定向诊断，不代表并发负载能力或生产响应承诺。新增两项真实数据库测试在强制通用计划、立即准备语句及单连接复用条件下，交替读取两个企业，检查结果隔离、执行时重新规划，以及事务结束后的设置恢复；既有全部待办环节测试继续检查查询语义和权限。

本次修复有实际超时与定向复现证据，不以延长页面等待或测试自动重试来掩盖问题；也不将此前未定位的其他详情加载超时一并宣布修复。

## 重复执行

按README启动开发数据库、身份服务、认证服务、业务API及管理端，并准备演示账号。不要并发运行会修改测试时钟、回收过期预占或重置数据的其他验证。首次连续营业场景在正常预占回收任务运行时通过；随后待办专项与相关页面回归期间暂停该任务，验证结束后恢复。

进入 `apps/admin-web` 执行：

```powershell
pnpm run test:continuous
```

每次生成独立试用企业，不复用既有库存。失败时不删除原单；若已建立尚未过账的盘点，会通过仓储账号取消该试用盘点以解除冻结。验收结果写入本机 `artifacts`，未包含密码、会话或令牌。

- `continuous-operations-manifest.json`：开通清单和岗位范围。
- `continuous-operations-reconciliation.json`：原单标识、岗位身份、逐节点核对及两次恢复结果。
- `continuous-operations-db.json`：独立数据库核对结果。
- `continuous-operations-ledger.png`：最终库存台账截图。

数据库核对使用正常业务运行账号，在租户隔离下开启只读、可重复读事务，检查实存3件、成本余额34.512元、14条库存流水、8条成本流水、应收应付0和单据最终状态。资金记录为零售实收40+20元、零售退款20元、批发收60元、采购付117元，净变动为-17元；该数只说明本次虚拟账户登记变动，不是银行余额或总账。

原 `verify_mainline_trial.py` 增加可选输入、输出路径，以同一套固定断言核对两个场景，默认调用保持兼容。核对脚本不是通用报表，不能对任意企业使用上述固定期望数。

本轮执行范围与证据见[跨岗连续营业验证](跨岗连续营业验证.json)。当前仍为开发验证版；下一步进入试用部署、隔离备份恢复演练和空白企业开账验收。
