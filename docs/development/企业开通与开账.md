# 企业开通与首次开账

更新：2026-10-17。版本0.24，业务库b0026、控制库c0016；开通能力最初随c0015交付。以下保留初次开通的两角色验收数据，最新七岗位、双批次、空仓采购及首笔结算请按[空白企业开账验收清单](空白企业开账验收清单.md)执行。

## 本轮解决的问题

原本只能用演示初始化建立企业，无法从零库存的新企业开始验收。现在平台操作人员可按明确的开通清单创建独立企业、一个经营主体、首个实体仓库与库位，并指定首批成员。完成后使用现有网站建档、审核、导入期初及办理首次交易。

开通工具不复制演示商品、客户、库存、成本或欠款；不创建或重置密码。当前入口是本机开发环境的平台命令，不是企业自助注册页，也不属于普通业务接口。

## 平台开通

1. 按README准备开发环境与两库迁移。升级c0015前备份控制库；本轮备份保存在本机忽略目录 `artifacts/backups/before-c0015-control.dump`，已检查归档目录可读。该检查不等同于恢复演练。
2. 核对首批成员身份：账号须已在身份系统及 `control.principal` 中建立映射，使用实际principal UUID，不能用登录名或Keycloak subject代替。已有企业的成员管理数据包含principal_id；也可由平台人员在控制库只读核对。不在本轮工具内自动创建身份。
3. 复制 [开通清单示例](../examples/enterprise-provisioning.example.json) 到本机私有工作目录，替换企业、主体、仓库及成员信息。示例中的三个UUID仅为占位；为每个新企业生成新的request_id，并填入两个真实成员ID。成功或失败重试均保留原request_id和原清单。
4. 根目录执行以下命令。清单只含企业资料、成员ID和角色，不放账号密码或连接信息。

```text
backend/.venv/Scripts/python.exe scripts/provision_enterprise.py .cache/enterprise-opening.json
```

Linux将解释器路径改为 `backend/.venv/bin/python`。脚本从本机开发配置读取两库连接：控制库使用迁移身份切换control_owner，业务库继续使用med_runtime和租户RLS。不得将平台凭据配置给网页或普通API。

清单要求2至20个不同成员，恰好一个OWNER，另有一名具备期初审核权的独立成员；最小组合是OWNER和QUALITY。每人最多配置3个现有角色，全部成员初始仅访问本经营主体。开通后可在“成员与权限”进一步分工，在“仓库与库位”增加实体仓库和库位。

成功输出tenant_id、entity_id、warehouse_id、location_id以及COMPLETED。这是该开通请求的完成记录；如果企业以后被停用，重跑原清单不会重新启用企业，也不会覆盖后续成员、仓库或业务资料。

## 中断与重试

控制库先创建不可访问的企业及成员，记录PENDING；业务库在一个事务内建立经营主体、仓库、库位及审计；两边完成并核对一致后，控制库在一个事务内启用企业及成员、记录COMPLETED。两库不是一个分布式事务。

| 结果 | 处理方式 |
| --- | --- |
| 清单字段或角色错误 | 修正未提交的清单；验证失败不写数据库。 |
| MEMBER_NOT_FOUND | 先核对身份映射，再用原清单重试；不会创建半套企业。 |
| 数据库异常或进程中断 | 确认服务和迁移就绪后，使用原清单重试。未完成的企业及成员保持停用，不出现在可选企业中。 |
| PROVISION_CONFLICT | 同一个request_id对应的内容与原清单不同。找回原清单，不要通过另换编号来绕过重复开通检查。 |
| PROVISION_INCONSISTENT | 未完成企业的资料已被其他平台操作改动。保持停用，平台人员核查审计及原清单，不能直接打开active来绕过核对。 |

同一request_id的并发操作串行办理；已完成的重复操作返回原结果。控制库已提交但业务库未成功时，恢复后继续建立业务资料；业务库已成功而启用阶段失败时，恢复后核对原资料并完成启用，不重复建立仓库或库存。

平台人员可用具备控制库管理权限的连接只读核对进度：

```sql
SELECT request_id, tenant_id, state, created_at, completed_at
FROM control.enterprise_provisioning
ORDER BY created_at DESC;
```

此表不向认证服务或普通运行角色授权。请求清单不可更改，已完成记录不可更新或删除。不同request_id会视作不同开通请求，目前不以企业名称或信用代码自动合并企业；平台须自行防止另建编号重复开通同一家企业。

## 企业首次营业顺序

1. OWNER和QUALITY分别登录，在企业切换框选择新企业。初始没有商品、往来单位和库存流水。
2. OWNER建立商品/SKU、供应商和客户，QUALITY核对资质后独立审核。资料中的有效期和经营范围需满足后续业务要求。
3. 有历史实物时，先在“期初库存”选择未使用的仓库，下载CSV模板，填入SKU编码、库位、批号、生产日期、有效期、基本单位数量及该行总成本，预览纠错后保存。QUALITY审核并启用，核对库存和成本台账。单仓最多200行，完整清单只能启用一次；开始正常入库后不能再补期初。
4. 没有历史实物的仓库可直接从采购开始，不必创建零数量期初。采购制单、独立审核、到货、验收、入库后，核对数量、成本及供应商应付。
5. 零售前先建立现金账户；批发赊销前设置客户授信。分别完成首笔零售交付和批发拣货、复核、出库，核对实际剩余库存、成本、客户应收和供应商应付。

期初只导入原有合格库存及账面成本，不自动产生供应商应付。历史应收应付余额、总账、银行余额、税务开账及受特殊监管业务不在本轮范围。

本机保留的完整验收企业为 **试用开账企业-37200f8f**，demo.owner和demo.quality可切换查看；demo.viewer未加入，无法读取该企业。所有资质和商品均为软件验证用虚拟资料。

重复执行验收：`pnpm --dir apps/admin-web run test:opening`。现在执行七岗位、两批次期初、另一个空仓首次采购、批零与结算场景，具体数量和成本按最新清单核对，不再按上面的历史数据断言。每次生成独立测试企业并保留业务记录，会增加测试账号可选企业数量；结果清单、台账截图与核对数据保存在artifacts忽略目录。初次结果保留在[企业开账验证](企业开账验证.json)，最新记录见[空白企业开账验收记录](空白企业开账验收记录.json)。
