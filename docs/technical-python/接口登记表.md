## 状态转换登记
审批DRAFT→SUBMITTED→APPROVED，驳回回DRAFT；关键内容变更重新审批。过账后不可修改关键字段。
预占ACTIVE可部分消费，余量为0后CONSUMED；释放剩余后RELEASED；冻结则INVALIDATED。只有剩余量才释放。
零售DRAFT→READY→PAID_PENDING_POST→COMPLETED；无款取消CANCELLED；付款未知PAYMENT_UNCERTAIN；已款失败由恢复单驱动完成或退款关闭。
付款确认记录CONFIRMED不因库存失败回退；退款是新事实，原付款可派生展示PARTIALLY_REFUNDED或REFUNDED。
上传READY→SENDING→AWAITING_RECEIPT→SUCCEEDED；可重试失败进入RETRYABLE_FAILED，永久失败进入MANUAL_REQUIRED。
## 外部平台边界
外部回调URL、签名、枚举及限流在取得对应平台正式文档后登记。通用Webhook不能替代各平台验签算法。内部事件订阅与平台上传任务独立授权。

## 0.13 在途损失已实现接口补充

前缀 `/api/v1/transfers/{id}/losses`：GET 列表空后缀及 `/{loss_id}` 使用 `transfers.read`；POST 空后缀创建和 `/{loss_id}/cancel` 使用 `transfers.loss.write`；POST `/{loss_id}/review` 使用 `transfers.loss.review`；POST `/{loss_id}/post` 使用 `transfers.loss.post`。新增 5 条路径、6 个操作，核心总计 87 条路径。

创建的 expected_version 是父调拨版本，其余写操作为损失单版本。申请固定原行、数量、批号和原因 / 依据，不预占库存；审核通过及核销时重验余量。父单损失结清状态为 CLOSED_WITH_LOSS，原调拨行新增 lost_qty，remaining_qty 扣除已核销损失。已收齐后允许取消或拒绝遗留损失申请，禁止再核销。权限、事务及防重见 [ADR 0013](../adr/0013-调拨在途损失核销.md)。

## 0.18 实现补充：采购关闭接口

新增 POST /api/v1/purchase-orders/{id}/close，核心 API 共 98 条路径。请求复用 Transition（expected_version、reason），权限 purchase.write，受 MED_PROCUREMENT_COMMANDS_ENABLED 开关、租户 / 主体范围、授权守卫、Origin、CSRF 和 Idempotency-Key 约束。响应含 id / version / fulfillment_state / closed_by / closed_at / close_reason / 本次关闭 lines。原 APPROVED + OPEN 转 APPROVED + CLOSED；原收货记录继续验收入库。详情新增逐行 closed_qty 和 unreceived_qty，remaining_qty 表示仍可到货数量。关闭事实不可重开，原金额不重算。


## 本轮回归补充：采购 / 销售 / 库存资料选项分页

本机持续验收后，商品与往来单位超过旧 200 条选项上限，导致采购 / 销售开单及库存查询页面无法完成加载。本轮将 purchasing/options、selling/options 与 inventory/options 增加 offset（默认 0，最大 100000），每类数组每页最多 200 条，返回 has_more、next_offset。需要完整目录的调用方必须继续取页，不能只用第一页判断商品或单位不存在。

管理端依次取页、按 ID 去重，加载期间企业上下文变化则停止本次加载；订单最终提交仍重新校验资格与主体范围。接口保持租户隔离和稳定名称 / ID 排序。分页之间目录变更不是一致快照，刷新后重新读取；目前仍加载完整下拉选项，超大目录的远程搜索和前端容量优化留待后续，不宣称生产大目录性能已验收。

新增 6 项真实 PostgreSQL 验证：206 个供应商 / 客户、库存 SKU 及仓库的跨页完整性、空尾页、类别数量不一致时的取页行为、主体和租户隔离及三个 HTTP 接口的 offset 边界。没有清空或停用演示资料来绕过旧上限。


## 0.19 实现补充：采购到货前变更

核心 API 共 100 条路径。新增 POST /api/v1/purchase-orders/{id}/revise：purchase.write；expected_version、reason、supplier_id、warehouse_id、lines（OrderLine，1–50 行）。成功返回 id、version、revision_no、state=DRAFT。主体及原订单号不能修改；任意到货后禁止修改。新版保存后，原制单人及本轮任一修改人不可批准；仍使用既有 approve / cancel。

新增 GET /api/v1/purchase-orders/{id}/history：purchase.read，offset 0–100000，返回 items / has_more，每页 50 条。item 包含 id、created_by、created_at、action、detail；purchase.revised 的 detail 包含 before / after 采购头及行快照、reason、revision_no、version。新审核 / 取消事件增加 agreement 快照，旧历史事件可能无快照。详情 order 增加 revision_no / revision_editors。

变更写入复用采购写开关、会话、企业上下文、Origin、CSRF、幂等键与提交前守卫。主要失败码：VERSION_CONFLICT、INVALID_STATE、PURCHASE_ALREADY_RECEIVED、PURCHASE_UNCHANGED、SEPARATION_REQUIRED，以及原商品 / 供应商 / 包装 / 数量资格错误。请求不接收 entity_id / 原行 ID，保存成功后须刷新详情再建到货行。


## 0.20 已实现：采购拒收退回

`POST /api/v1/receipts/{id}/rejected-handovers`：`purchase.receive` 权限；复用采购写开关、会话 / CSRF / 主体守卫和幂等键。请求包含 `expected_version`（到货记录版本）、`handover_ref`、`recipient`、`reason` 及 `lines[{receipt_line_id,qty}]`，数量按基本单位用十进制字符串传入；行不可重复。只接受已拒收且未退回数量，不允许退回待验或合格数量。

成功返回交接 ID、到货 ID、新到货版本。订单关闭、供应商停用或商品冻结不阻止未入库拒收品实物交接；原订单已收数量保持不变。该命令仅结清保管，不执行存货 / 成本 / 应付 / 退款过账。

采购详情的到货行新增 `rejected_returned_qty`、`rejected_pending_qty`，`custody_qty = qty - posted_qty - rejected_returned_qty`。到货对象新增 `rejected_handovers`，包含逐行商品批号、数量、交接凭据、接收方、说明及操作者 / 时间。


## 0.21 已实现：仓库期初库存

- `GET /api/v1/inventory-openings/options`、`GET /api/v1/inventory-openings`：`entity_id` 必填，`offset` 0–100000；选项每页 200，列表每页 50。读取权限 `inventory.read`。
- `POST /api/v1/inventory-openings`：`opening.write`；请求 `client_operation_id`、`entity_id`、`warehouse_id`、`source_ref`、`reason`、`lines[sku_id,location_id,lot_no,mfg_date,expiry_date,qty,cost_amount]`。数量和金额为十进制字符串；1–200 行，同商品 / 批号 / 库位不能重复。成本是该行总额，最多两位小数。
- `GET /api/v1/inventory-openings/{id}`：清单、商品快照、审核信息、成本合计及过账 ID。
- `POST .../{id}/review`：`opening.review`；`expected_version`、`decision=APPROVE|REJECT`、`evidence_ref`、`reason`，制单人不可审核。
- `POST .../{id}/cancel`：`opening.write`；`expected_version`、`reason`，仅 DRAFT / APPROVED。
- `POST .../{id}/post`：`opening.post`；`expected_version`、`reason`，仅独立审核后启用，制单人不可执行；已成功过账返回同一永久结果。

新增 `opening_commands_enabled` 开关，默认关闭。本机开发脚本开启。所有写入复用会话 / CSRF / 主体 / 提交前守卫，创建另使用持久操作 ID 防重。新增库存流水类型 `OPENING_BALANCE`，不生成应付或收付款；过账按当前业务日与开放会计期间执行。

## 0.22 已实现：销售分配前变更

- `POST /api/v1/sales-orders/{id}/revise`：`sales.write`；请求 `expected_version`、`reason`、`customer_id`、`warehouse_id`、`delivery_address`、`minimum_shelf_days`、`credit_days`、`lines[sku_id,packaging_id?,qty,unit_price,tax_rate]`。固定原经营主体，禁止传 `entity_id`；商品行 1–50 条，数量与金额仍为十进制字符串。返回版本、DRAFT 状态、revision_no 与 released_exposure。

- 销售详情新增 `order.can_revise`、`revision_no`、`revision_editors`。保存变更重建商品行 ID；必须重新读取后再分配。

复用销售写开关、CSRF、幂等、版本、租户主体及提交授权守卫。已存在任何分配 / 发货历史（包括取消）时返回 `SALES_ALREADY_STARTED`；无实际内容变化返回 `SALES_UNCHANGED`；制单人 / 本轮修改人不能审核。已批准单修改释放旧客户占用；重新批准按新客户和新金额重新校验并占用信用，不变更历史应收或库存。当前核心 API 共 109 条路径。

## 0.23 已实现：原单退货进度与办理

- `GET /api/v1/returns/sources/{id}` 新增可选 `offset=0`，范围 0–100000，按原 `posting_id` 查询退货记录，每页 50 条。
- 原 `source` / `lines` / `partial_supported` 保留；`source.returned_amount` 为该原过账所有 POSTED 退货的累计含税金额。
- 新增 `active_return: {id,number,state} | null`，只返回非 POSTED / CANCELLED 申请，不受历史翻页影响。
- 新增 `history: {items:[{id,number,kind,state,gross_amount,reason,created_at}],has_more}`；按创建时间倒序、ID 排序，包含取消记录。金额和数量仍为十进制字符串。
- 复用 `returns.read`、会话上下文、租户 RLS 和经营主体范围检查。不同原过账（包括同一订单多次出库）的记录互相隔离。
- 前端直接使用采购详情 `receipts[].postings[].posting_id`、销售详情 `shipments[].posting_id` 进入原单退货。创建 / 收货 / 复核 / 过账 / 退款 API 不变；新的进度页不直接修改库存、成本或往来。

核心 API 仍为 109 条路径，无新增写开关、角色权限或数据库迁移。

## 0.24 已实现：同仓移库

- `GET /api/v1/location-moves/candidates`：entity_id 必填，search 最长 100，offset 0–100000；按商品 / SKU / 批号查询实体仓自有合格普通批次，50 条 / 页，显示未占用数量。读取权限 `transfers.read`。
- `GET /api/v1/location-moves/destinations`：entity_id、balance_id 必填，offset 0–100000；仅同仓其他库位，200 条 / 页，含 has_more / next_offset。
- `GET /api/v1/location-moves`：entity_id、offset，50 条 / 页；`GET .../{id}` 返回 document、固定 item 和已过账 result。
- `POST /api/v1/location-moves`：`transfers.write`，body 为 client_operation_id、entity_id、balance_id、destination_location_id、qty、lot_no、reason；qty 为基本数量十进制字符串，按 SKU 精度验证。返回 id / number / state / version。
- `POST .../{id}/review`：`transfers.review`；expected_version、reason、decision=APPROVE|REJECT，必须独立审核。
- `POST .../{id}/cancel`：`transfers.write`；expected_version、reason，仅 DRAFT / APPROVED。
- `POST .../{id}/post`：`transfers.dispatch`；expected_version、reason、lot_no、confirmed=true；需要独立审核，重新核对当前库存及批次资格，结果包含 posting_id、qty、cost_delta=0、source_balance_id 和 destination_location_id。

## 0.25 已实现：单据商品快捷检索

- `GET /api/v1/catalog/entry-products`：entity_id必填，channel为purchase或sale；分别需主体范围内purchase.read或sales.read。search最长100字符，空格拆词同时匹配名称、SKU/商品编码、规格、厂家、通用名、别名、商品名、器械型号；使用参数化字面匹配，精确SKU编码优先。offset默认0、范围0–100000，每页20条，返回items与has_more。
- items包含id、code、name、product_code、base_unit、qty_scale、specification、manufacturer_name、generic_name、search_alias、trade_name、device_model和eligible。一般检索仅返回已审核、有效期内、当前主体未冻结且符合已开放流程的商品；销售沿用批次管理要求。不能据此保证某供应商经营范围、包装可用性、信用或可售数量，提交仍执行原业务校验。
- 可选sku_id用于改单回显已选商品，允许读取当前企业内已不可选的原商品，但返回eligible=false；不跨租户读取，不能用来绕过提交校验。分页不是目录快照，不宣称超大目录性能已验收。
- `GET /api/v1/purchasing/options` 与 `GET /api/v1/selling/options` 追加include_skus，默认true保持兼容；传false时skus为空，has_more按其余数组判断，往来单位、仓库及库位仍沿用分页。采购、批发新建/改单已采用此模式并独立检索商品。
- 所有读取仍校验会话、上下文代次、权限和主体范围；数据库继续强制租户隔离。共122条已实现路径，无新增迁移、权限及依赖。
