# 采购四环节工作区实施与验收

实施日期：2026-10-20。依据用户提供的 `purchase-workflow-compact-tabs.html` 与 `codex-purchase-compact-ui-implementation.md`。原型中的模拟商品、单号、数量和流转脚本没有进入业务实现。

## 1. 实施范围

在现有 Vue / FastAPI 系统内改造，沿用顶部导航、工作标签、独立订单编辑页、草稿保护、权限体系、统一日期组件和原有写入接口。没有迁移、重建或批量改写旧单据；没有改动零售界面。

一个全局“采购入库”工作页包含四个内部页签。首行左侧为业务页签，右侧为当前环节按钮；紧接查询条件和表格。移除原列表大标题和四步流程说明条。表格区域滚动，分页位于其外部，避免被最后一行覆盖。

| 内部页签 | 默认列表与主操作 | 历史入口 |
|---|---|---|
| 采购订单 | 所有订单；新建采购订单、刷新订单、我的草稿 | 订单执行记录，同一订单查询，展示审批与履行进度两个维度 |
| 采购收货 | 已审核、未关闭且有待收余量的订单；登记收货 | 每次实际收货记录 |
| 采购验收 | 仍有待验数量的收货记录；开始验收 | 每次已记录的验收结论，含合格与不合格数量 |
| 采购入库 | 验收合格且尚未过账的结果；确认入库 | 每次已过账的入库记录 |

主操作先选定一条来源，或从具体行进入；不会隐式批量办理。入口读取最新订单详情后再次检查状态，再打开既有办理表单。最终提交仍由后端校验权限、版本、人员分离与数量。

没有使用虚构待办数量，也没有把记录总数冒充待办数。页脚显示“本页条数 / 当前页 / 已选条数”，以 50 条分页。

## 2. 导航、联查与状态保持

采购菜单保持原来的浮层展开机制，分两栏：

- 业务办理：采购订单、采购收货、采购验收、采购入库、我的草稿。
- 记录查询：订单执行记录、收货记录、验收记录、入库记录。

这些入口都定位到同一个全局工作页。没有增加尚无数据来源的分析报表。鼠标进入、延迟离开、点击、Esc、方向键、边缘定位仍沿用公共导航行为。

列表按“经营主体 + 业务环节 + 待办/历史”隔离。访问过的视图保留挂载，切换时保留查询草稿、已执行条件、日期输入、更多条件展开、分页、日期排序、选中行和横纵滚动位置。已执行条件与当前页签还按原有租户/用户缓存命名空间保存在当前浏览器会话中。浏览器刷新后不保证恢复尚未执行的查询文字或滚动位置；单据草稿仍由原草稿机制保存。

打开来源订单、收货记录、验收结论和入库结果使用原独立记录标签，返回时保留采购工作区状态。验收历史会展开并定位到相应结论；入库记录定位到相应入库结果。旧详情内的商品、批号、验收明细、拒收退回、入库及退货入口全部保留。

办理成功发出采购刷新通知，当前列表刷新，其余已访问视图在再次激活时更新。请求以递增版本隔离，卸载后丢弃晚返回结果。查询失败保留上一份数据并明确提示，禁止从失败结果直接办理。

### 新增只读接口

`GET /api/v1/purchasing/workflow`

参数：`entity_id`、`stage=orders|receiving|inspection|posting`、`view=pending|history`、`offset`、`search`、`state`、`date_from`、`date_to`、`warehouse_id`、`party_id`、`sort=newest|oldest`。

沿用北京时间日期区间、后端权限 `purchase.read`、经营主体范围和数据库租户隔离。SQL 表达式只来自固定代码，用户参数绑定。每页最多 50 条，额外读取一条确定 `has_more`，没有逐条调用详情接口。

返回来源订单、收货、验收和入库结果的真实标识、真实单号、时间、状态、可执行动作和按基本单位分组的数量。没有独立验收单号的历史显示来源收货单号及验收时间，不编造业务编号。长单号在列表截断并保留完整悬停文本。

日期含义按视图显示：订单日期、收货日期、验收日期；已入库历史使用实际过账日期。搜索支持单号、来源订单号、供应商名称或编码。不同环节状态不交叉混用。

### 保留的接口

- `GET /api/v1/purchasing/options`、`GET /api/v1/purchase-orders/{id}`、原订单列表及修改历史接口。
- 原订单新建、修改、审核、取消、关闭未收余量接口。

## 4. 数量模型与边界

当前真实关系为：采购订单行 → 多次收货明细 → 多次验收明细 → 每次验收对应的合格入库结果 → 库存/成本/应付记录。

- 待收 = 订购 − 实收 − 已关闭余量。
- 待验 = 实收 − 已合格 − 已不合格。
- 待入库只来源于尚未过账的合格结果。
- 入库后才增加可用库存、成本和应付；不合格与尚待验数量不得计入。
- 列表摘要按基本单位分组；不同单位不相加。商品/批号维度的原始明细保留在详情中。

**尚未支持的三个独立业务语义：**

1. 收货时拒收：原到货接口仅记录实收，没有“本次到场、收货拒收数量/原因”的独立事实。订单 100、实际登记 90 时，当前待收仍是 10，不能把这 10 自动解释成拒收；后续可继续收货或按原机制关闭余量。
2. 暂缓验收：可留下待验余量，但没有独立的暂缓数量、原因与解除记录。合格 70、不合格 15、余量 5 时，这 5 标注“待验”，不能声称已登记暂缓结论。
3. 同一份合格结果分次入库：一份合格 70 的结果当前一次过账 70；可以分次验收形成多份结果，但不能将同一份结果直接按 40、30 再次拆分。该场景本次未实现。

后续最小增量建议：分别增加收货拒收事实及原因、暂缓/解除事实与剩余可验量校验、合格结果下的多次入库明细与累计已入库量。沿用原事务、明细锁和幂等机制，保持旧记录可读，不将未办理余量默认为拒收或暂缓。本次不扩大这三项设计。
